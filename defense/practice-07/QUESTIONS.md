# Запитання викладача та відповіді (№7)

1. **Що таке CI?** Continuous Integration: автоматична перевірка змін (встановлення залежностей, lint, тести та збірка).
2. **Чим CI відрізняється від CD?** CI перевіряє зміни, а delivery готує та публікує результат, який можна розгорнути.
3. **Що таке GitHub Actions workflow?** YAML-файл із подіями запуску, jobs та steps, який виконується на GitHub runner.
4. **Навіщо `push` і `pull_request`?** Щоб перевіряти оновлення main та код перед злиттям.
5. **Чому `npm ci`, а не `npm install`?** `npm ci` встановлює залежності точно за lock-файлом і підходить для відтворюваного CI.
6. **Що дає кеш npm?** Прискорює повторні встановлення, зберігаючи кеш завантажених пакетів.
7. **Що саме перевіряє lint?** У цьому проєкті `node --check` перевіряє синтаксис JavaScript; це не повний аналіз стилю ESLint.
8. **Чому два Docker-образи?** Власні сервіси TaskFlow: статичний фронтенд на Nginx і Node.js API. PostgreSQL є готовим стороннім образом.
9. **Що таке GHCR?** GitHub Container Registry: реєстр, де зберігаються опубліковані Docker-образи.
10. **Як працює `GITHUB_TOKEN`?** GitHub видає тимчасовий токен workflow; job `publish` має `packages: write`, щоб завантажувати образи без власного PAT.
11. **Навіщо тег `v1.0.0` та `sha-...`?** Версія зручна для релізів; SHA дозволяє пов'язати образ із конкретним комітом.
12. **Для чого Dependabot?** Пропонує оновлення npm-пакетів і GitHub Actions через окремі pull requests.
13. **Навіщо concurrency?** Щоб скасувати застаріле виконання для тієї самої гілки та не витрачати runner-час.
14. **Чому публікація не запускається на кожен push?** Щоб випадково не публікувати проміжні версії. Публікація лише вручну або за тегом `v*`.
15. **Що показує Job Summary?** Коротку підсумкову інформацію про CI та опубліковані образи всередині конкретного run.
16. **Що робити при червоному CI?** Відкрити failed job, прочитати лог, відтворити помилку локально, виправити, виконати новий push.
