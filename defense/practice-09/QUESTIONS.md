# Питання для самоперевірки

1. **Що таке Kubernetes Cluster?** Сукупність керуючих компонентів і Node-ів, на яких оркеструються застосунки.
2. **Що таке Node?** Фізична або віртуальна машина, на якій можуть працювати Pod-и.
3. **Що таке Namespace?** Логічний простір імен для групування namespaced-ресурсів, а не фізична машина.
4. **Чим Pod відрізняється від контейнера?** Pod — найменша одиниця розгортання Kubernetes, яка може містити один або декілька контейнерів зі спільним мережевим контекстом.
5. **Для чого Deployment?** Задає бажаний стан, кількість реплік і шаблон Pod-а; через ReplicaSet підтримує їх і керує оновленнями.
6. **Для чого Service?** Надає стабільну адресу доступу до групи Pod-ів, вибраних за labels. ClusterIP доступний всередині кластера.
7. **Для чого Ingress?** Описує правила HTTP(S)-маршрутизації за доменом і шляхом; виконує їх Ingress Controller.
8. **Навіщо дві репліки?** Щоб зменшити вплив відмови одного Pod-а; для відмовостійкості на рівні Node-ів потрібне рознесення, а БД потребує окремого рішення.
9. **Як надходить код у Pod?** GitHub Actions збирає й публікує образ у GHCR, Deployment визначає його тег, kubelet забезпечує отримання образу. Публікація образу сама по собі не розгортає нову версію.
10. **Чому спільна PostgreSQL?** Обидва API Pod-и мають працювати з однаковими даними, а не з незалежними локальними SQLite-файлами.
11. **Який шлях запиту?** DNS-резолвінг, HTTP-з'єднання з Load Balancer, Ingress Controller, Service та готовий Pod.
12. **Чи запущено цей кластер?** Ні, у №9 представлено теоретичний дизайн. Практичне розгортання належить до №10.
