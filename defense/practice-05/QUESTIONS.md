# Запитання та відповіді для захисту №5

**1. Що таке ідемпотентність?**  Повторне виконання логічно тієї самої операції не повинно створювати додаткових побічних ефектів. Для POST використовуємо `Idempotency-Key`.

**2. Де зберігаються ключі?** У SQLite-таблиці `idempotency_keys`. Створення завдання та фіксація ключа входять в одну транзакцію.

**3. Що відбудеться при повторному POST?** Якщо ключ і JSON ті самі, сервер поверне збережену відповідь 201 із тим самим ID. Якщо JSON інший, поверне 409.

**4. Навіщо `X-Request-Id`?** Щоб співвіднести клієнтський запит з відповідями та діагностичними записами. Він є в заголовках відповідей і в тілі помилки.

**5. Що таке exponential backoff?** Зростаюча затримка між повторними спробами, наприклад 300, 600, 1200 мс.

**6. Що таке jitter?** Невелика випадкова добавка до затримки, яка запобігає одночасним повторним запитам від багатьох клієнтів.

**7. Навіщо `Retry-After`?** Сервер підказує клієнту, скільки зачекати після HTTP 429 перед наступним запитом.

**8. Чим корисний `AbortController`?** Дає можливість контрольовано зупинити надто довгий запит. У демо `/health` скасовується через 1 секунду.

**9. Що таке degraded mode?** Тимчасовий обмежений стан інтерфейсу після трьох послідовних збоїв. Кнопки CRUD на 8 секунд вимикаються, з'являється попередження.

**10. Чому PATCH/DELETE не повторюються автоматично?** Без окремих гарантій ідемпотентності це може призвести до небажаних наслідків. У навчальній реалізації повтори дозволені для GET та POST з ключем.

**11. Як працює rate limiter?** Він підраховує POST-запити з IP-адреси за 10 секунд. Після 8 запитів повертає 429 із `Retry-After`.

**12. Чому збої демонстраційні, а не випадкові?** Випадкові 500/503 ламають звичайну роботу. Натомість демонстраційний режим вмикається окремо й діє лише на localhost.
