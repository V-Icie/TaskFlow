# Бізнес-документ TaskFlow

**Версія:** 1.0  
**Практична:** №2 «Бізнес-документ і архітектурна діаграма»  
**Призначення:** навчальний командний проєкт із вебпрограмування.

## 1. Назва та короткий опис

**TaskFlow** — простий вебзастосунок для обліку й організації особистих завдань. Користувач переглядає перелік справ у браузері, а сервер отримує актуальні дані з бази та повертає їх через HTTP API. Система орієнтована на студентів та інших користувачів, яким потрібен зрозумілий спосіб планування щоденних справ без громіздкого функціоналу.

На етапі практичної №1 реалізовано мінімальну взаємодію **браузер → Node.js/Express → SQLite**: кнопка **Load items** звертається до `GET /items`, що читає записи з таблиці `items (id, name)`. У наступних практичних заплановано модель завдань, повноцінний CRUD API, перевірку вхідних даних і керування статусами.

Розвиток TaskFlow відбуватиметься поступово: спочатку документування й опис домену, потім реалізація функцій, а згодом контейнеризація, автоматичне тестування та моніторинг. Важливо розрізняти **наявні** функції від **запланованих**, щоб презентація проєкту точно відображала його поточний стан.

## 2. Користувачі та ролі

| Роль | Призначення | Статус |
|---|---|---|
| Відвідувач демонстрації | Відкриває сторінку й переглядає тестові записи | Реалізовано в №1, без входу |
| Користувач | Керує власними завданнями, статусами, категоріями | Заплановано |
| Адміністратор (необов'язковий) | Адмініструє тестове середовище, переглядає стан сервісу | Потенційна майбутня роль; не входить у MVP |

**Примітка:** аутентифікацію ще не реалізовано, а поділ на ролі наразі є частиною проєктування, а не діючої системи доступу.

## 3. Основні сценарії використання

1. **Перегляд списку (вже працює).** Відвідувач відкриває головну сторінку, натискає **Load items** і бачить елементи, отримані з бази через API.
2. **Створення завдання (заплановано).** Користувач вводить назву та натискає «Додати»; система перевіряє дані й зберігає нове завдання.
3. **Оновлення завдання (заплановано).** Користувач змінює назву або статус існуючого завдання; дані оновлюються в БД.
4. **Завершення та фільтрація (заплановано).** Користувач позначає завдання виконаним і фільтрує список за статусом.
5. **Видалення завдання (заплановано).** Користувач видаляє непотрібний запис і отримує підтвердження змін.

## 5. Нефункціональні вимоги

- **Зручність:** інтерфейс має бути зрозумілим без окремого навчання, із помітними станами завантаження й помилок.
- **Продуктивність:** ціль для локальної демонстрації — типовий запит списку до 1 секунди на невеликій тестовій БД; це ціль проєкту, а не виміряна гарантія.
- **Надійність:** помилки сервера не мають призводити до зависання сторінки; надалі передбачено таймаути й повтори без створення дублікатів.
- **Безпека:** введені дані перевіряються на сервері, SQL виконується через параметризовані запити; у репозиторій не комітяться секрети чи локальні БД.
- **Підтримуваність:** розділення фронтенду, HTTP-обробників і роботи з БД; тести та README.
- **Переносимість:** застосунок повинен запускатися на Windows через Node.js; контейнеризація запланована окремим етапом.

## 6. Обмеження та те, чого система не робитиме

- Не реалізує онлайн-платежі, замовлення товарів і доставку.
- Не є корпоративним планувальником з обліком робочого часу та зарплат.
- Не має мобільного нативного застосунку на поточному етапі.
- Не підтримує одночасне редагування завдання кількома людьми в реальному часі.
- Не гарантує роботу офлайн або синхронізацію між пристроями без сервера.
- Не заявляє про наявну авторизацію, поки її не реалізовано.

## 7. Критерії приймання та поточний стан

- **Є зараз:** працюючі `GET /items`, SQLite-таблиця `items`, кнопка завантаження, README й тести бази з практичної №1.
- **Після наступних ітерацій:** моделі домену, CRUD для завдань, OpenAPI, валідація та перевірки.
- **Спосіб підтвердження:** локальна демонстрація, тести, код у GitHub, документи в `docs/`.
