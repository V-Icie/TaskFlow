# Практична №3: Ubiquitous Language (глосарій TaskFlow)

| Термін | Єдине визначення | Контекст |
|---|---|---|
| Домен | Предметна область планування особистих справ | Усі |
| Піддомен | Частина бізнес-задачі з окремою відповідальністю | Усі |
| Bounded Context | Межа, всередині якої терміни й правила мають одне значення | Усі |
| Користувач (`User`) | Особа з ідентифікатором і відображуваним ім'ям | Identity |
| Завдання (`Task`) | Справа з назвою, власником та станом виконання | Tasks |
| Власник (`ownerId`) | Ідентифікатор користувача, чиїм є завдання або категорія | Tasks, Categories |
| Категорія (`Category`) | Названа група для впорядкування завдань | Categories |
| Статус завдання | Одна з позначок `open` або `done` | Tasks |
| Завершення | Перехід завдання зі стану `open` до `done` | Tasks |
| Елемент (`Item`) | Спрощений запис `items(id, name)` з практичної №1, **не рівнозначний** повній сутності `Task` | Старий API |

## Уточнення неоднозначностей

- **«Елемент» vs «Завдання»:** `Item` використовується лише для навчального `GET /items`; `Task` має статус, власника та необов'язкову категорію. У №4 планується окремий `/tasks` API.
- **«Користувач» vs «Власник»:** `User` — доменна сутність Identity Context, а `ownerId` — лише посилання на її ідентифікатор в інших контекстах.
- **«Категорія» vs «Статус»:** категорія групує справи за змістом, а статус описує виконання. Категорія не є статусом.

Ці назви використовуються в документації та прототипі, щоб різні контексти не вкладали різних значень у ті самі слова.
