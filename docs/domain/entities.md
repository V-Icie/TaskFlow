# Практична №3: сутності та піддомени TaskFlow

## Домен

**Планування особистих завдань**: користувач упорядковує справи, стежить за виконанням та групує їх за категоріями. На відміну від технічного поділу на frontend/backend/database, піддомени відображають поняття предметної області.

| Піддомен | Bounded Context | Основна відповідальність | Сутності |
|---|---|---|---|
| Користувачі | Identity Context | Ідентифікаційні дані власника завдань | `User` |
| Керування завданнями (основний) | Tasks Context | Створення, опис і життєвий цикл завдання | `Task` |
| Категоризація (допоміжний) | Categories Context | Назви категорій та класифікація завдань | `Category` |

## Ключові сутності та атрибути

### `User` (Identity Context)
- `id: number` — додатний ідентифікатор.
- `displayName: string` — непорожнє ім’я для показу.
- Метод `rename(name)` — змінює ім’я з перевіркою.

### `Task` (Tasks Context)
- `id: number` — додатний ідентифікатор.
- `title: string` — непорожня назва завдання.
- `ownerId: number` — ID власника, що походить із Identity Context.
- `categoryId: number | null` — необов’язкове посилання на категорію.
- `status: 'open' | 'done'` — стан завдання.
- Методи `rename(title)`, `complete()`, `reopen()`, `assignCategory(id | null)`.

### `Category` (Categories Context)
- `id: number` — додатний ідентифікатор.
- `name: string` — непорожня назва категорії.
- `ownerId: number` — власник категорії.
- Метод `rename(name)`.

## Межі та правила

1. **Tasks Context** керує станом завдань, а не обліковими записами.
2. **Identity Context** є джерелом інформації про користувача; Tasks і Categories зберігають лише `ownerId`, не копіюючи профіль.
3. **Categories Context** визначає категорію, але не змінює статус завдання.
4. Відповідність `ownerId` та належність категорії власникові має перевіряти прикладний сервіс у наступних ітераціях; поточні окремі класи не звертаються до БД.
5. Відсутність авторизації у практичній №1 не означає, що вона вже реалізована для `User`.

## Стан реалізації

- **Реалізовано раніше:** SQLite `items(id, name)`, `GET /items`, кнопка `Load items`.
- **Реалізовано в №3:** незалежні JS-класи `User`, `Task`, `Category`, їхні мінімальні методи та тести.
- **Заплановано для №4:** CRUD API та збереження повноцінних завдань, перетворення між DTO і доменною моделлю.
- **Не реалізовано:** автентифікація, зв'язок між моделями та наявною таблицею `items`, перевірки належності між контекстами.
