# ADR 0003: REST, HTTP-статуси, модель помилок

- **Дата:** 2026-11-23
- **Статус:** Прийнято

- REST з JSON, маршрути `/tasks` та `/tasks/{id}`.
- Створення: POST → 201; список/читання: GET → 200; редагування: PATCH → 200; видалення: DELETE → 204 без тіла.
- Некоректний ввід → 400; невідомий task ID → 404; несподівана внутрішня помилка → 500.
- Єдиний формат: `{ "error": "ValidationError", "code": "TITLE_REQUIRED", "details": [{ "field": "title", "message": "Title is required" }] }`.
- Контракт: `docs/api/openapi.yaml`, реалізація має відповідати схемам і статусам.
- `GET /health` повертає `{ "status": "ok" }`.
- Сумісність: `GET /items` із №1 не змінюється.
- Обмеження: навчальна версія поки не має авторизації: власник завдання умовно `ownerId=1`.
- Кореляція помилок через `X-Request-Id` запланована до практичної №5.

## Доповнення для практичної №5

- Кожна HTTP-відповідь включає заголовок `X-Request-Id`, який створює сервер або приймає від клієнта після перевірки формату.
- Усі JSON-помилки повертають `error`, `code`, `details`, `requestId`.
- `POST /tasks` потребує `Idempotency-Key`: той самий ключ із тим самим тілом запиту повторно повертає вихідний статус 201 і той самий JSON. Ключ із іншим тілом повертає 409.
- Ідемпотентні результати зберігаються в SQLite разом із завданням в одній транзакції; тестова БД не очищується між перезапусками.
- Rate limiting на `POST /tasks`: максимум 8 запитів за 10 секунд на клієнтську IP-адресу; 429 містить `Retry-After`.
- Клієнт повторює GET, а також POST лише з ідемпотентним ключем, при мережевих помилках та 5xx/429. PATCH/DELETE автоматично не повторюються для уникнення небезпечних дублікатів ефектів.
- Демонстраційні збої вмикаються тільки через `DEMO_FAILURES=1` і доступні лише із localhost. Це не виробнича функція.
